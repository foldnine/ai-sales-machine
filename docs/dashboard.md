# Dashboard

The operator's web console: `dashboard/`, a Next.js app that runs as one
container (`aisales-dashboard`) on `127.0.0.1:3000`. It shows the pipeline
and lets you approve, edit or reject drafts. It is the only part of the
stack a person clicks through every day, so it is also the part with the
narrowest access.

## Pages

| Page | What it answers |
|---|---|
| **Overview** | How much was found, drafted, sent and answered; what is waiting for you; are the agents healthy |
| **Approvals** | Should this message go out? The draft, the recipient, the signals and research behind it, the score breakdown, and why autosend held it (if it did) |
| **Companies** | What do we know about this company, and how do we know it? Facts with sources, inferences, unknowns, contacts, messages, agent runs |
| **Outreach** | Every message and its state: awaiting approval, approved, sent, replied, bounced, rejected (with the reason) |
| **Replies** | Every answer, classified, with the conversation's state and deal value |
| **Performance** | Which segments, campaigns and message variants turn into conversations and revenue |
| **System** | The sending switches, agent health, recent failures, the Telegram outbox and the dashboard's own audit log |

Keyboard on the approval queue: `j` / `k` next and previous, `a` approve,
`e` edit, `r` reject, `Esc` cancel, `⌘/Ctrl + Enter` save or confirm.

## Access model

Approving from a browser is a second way to cause a send. It is built so
that it can do less than the workflows can, not more:

1. **Its own database role.** The dashboard connects as `aisales_dashboard`
   (`postgres/migrations/0033_dashboard.sql`), never as the owner of the
   schema. The role has `SELECT` on the `public` schema and nothing on the
   `n8n` schema, where n8n keeps its encrypted credentials.
2. **No table writes.** The role cannot `INSERT`, `UPDATE` or `DELETE`
   anything. Its only writes are three `SECURITY DEFINER` functions:

   | Function | Does |
   |---|---|
   | `dashboard_approve(ids, actor)` | `pending_approval` → `approved`, records who and when, moves the lead. Exactly the `/approve` update in WF-11 |
   | `dashboard_reject(id, reason, actor)` | `pending_approval` → `rejected` with the reason |
   | `dashboard_edit(id, subject, body, actor)` | Changes a waiting draft's text. **Refused if the signature and opt-out block below the `--` line is changed or removed** |

   Each one writes a row to `operator_actions` in the same statement as the
   change. An edit keeps the previous text there.
3. **Approving is not sending.** An approved draft is a row with a status.
   WF-06 is still the only thing that sends, and only inside
   `OUTREACH_PAUSED`, the daily limit, the send window and the suppression
   trigger, which also fires on the dashboard's update.
4. **Switches are read-only.** `OUTREACH_PAUSED`, the autosend master switch,
   limits and the send window are shown on the System page and cannot be
   changed from the dashboard. They stay in `.env` and on Telegram.
5. **One operator, one password.** `DASHBOARD_PASSWORD` in `.env`, compared
   in constant time. Five failed attempts per client in fifteen minutes lock
   the login. The session is a signed, `HttpOnly`, `SameSite=Lax` cookie
   (`DASHBOARD_SESSION_SECRET`), valid for seven days, and `Secure` when the
   request came in over HTTPS. Server Actions reject cross-origin posts.
6. **Loopback only, read-only container.** Bound to `127.0.0.1`, read-only
   root filesystem, `no-new-privileges`, runs as the unprivileged `node`
   user.

`postgres/tests/dashboard.sql` proves the role cannot update `outreach`
directly, cannot read n8n's credentials, cannot strip the signature, and that
every action is logged.

## Remote access

Keep the bind on loopback and put Tailscale in front of it:

```bash
tailscale serve --bg --https=8443 3000
```

That serves `https://<machine>.<tailnet>.ts.net:8443`, visible only to your
tailnet, with a valid certificate. The session cookie becomes `Secure`
automatically. If your browser reports *"Invalid Server Actions request"*
behind a proxy that rewrites the `Host` header, the proxy is the problem:
`tailscale serve` does not do that.

## Configuration

| Variable | |
|---|---|
| `DASHBOARD_PASSWORD` | The login. Generated by `make init`; change it whenever you like and `make restart SERVICE=dashboard` |
| `DASHBOARD_SESSION_SECRET` | Signs the session cookie. Changing it signs everyone out |
| `DASHBOARD_DB_PASSWORD` | Password of the `aisales_dashboard` role. After changing it run `make dashboard-role` |
| `DASHBOARD_BIND_ADDR`, `DASHBOARD_PORT` | `127.0.0.1` and `3000`. Keep the address on loopback |

## Troubleshooting

| Symptom | Fix |
|---|---|
| `make health` says the dashboard cannot reach the database | The role has no password yet: `make dashboard-role`, then `make restart SERVICE=dashboard` |
| The page says *Dashboard is not configured* | An old `.env`: `make env-upgrade APPLY=yes`, then `make up` |
| Everything is empty | Nothing has run yet. Activate WF-01 to WF-05 (README, *Turn it on*). To look around first, run `make seed-demo` on a throwaway install |

## Development

```bash
cd dashboard
npm ci
cp .env.local.example .env.local   # point DATABASE_URL at a development database
npm run dev                        # http://localhost:3000
npx tsc --noEmit                   # what CI runs, plus `npm run build`
```

A development database: `make up && make migrate && make seed-demo` on a
throwaway install, then `make dashboard-role` and use
`postgres://aisales_dashboard:<DASHBOARD_DB_PASSWORD>@127.0.0.1:5432/aisales`.

Conventions:

- **SQL lives in `lib/queries/`**, as plain parameterised SQL (postgres.js
  tagged templates). Cast counts to `int` and rates to `float8` in the query
  so the page receives numbers.
- **Every page and action calls `verifySession()` first.** `proxy.ts` only
  redirects when there is no cookie at all; it is not the security check.
- **New writes are new SQL functions**, in a new migration, granted to
  `aisales_dashboard`, logging to `operator_actions`, with a test in
  `postgres/tests/`. Never grant the role a table write.
- **Design tokens are in `app/globals.css`.** Use the semantic colours
  (`bg-surface`, `text-fg-muted`, `bg-accent`), not raw palette values.
- This is Next.js 16: middleware is `proxy.ts`, request APIs are async. Read
  `dashboard/AGENTS.md` and the bundled docs in
  `node_modules/next/dist/docs/` before changing framework-level code.
